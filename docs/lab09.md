# ЛР-9. Балансування навантаження та доступність

Код: [`labs/lab09-load-balancing`](../labs/lab09-load-balancing) · повний вивід: [`results/experiment-output.txt`](../labs/lab09-load-balancing/results/experiment-output.txt)

## Архітектура

```
                         ┌──▶ app1 (172.28.0.11) ─┐   :8001 — прямий доступ (порівняння)
client ─▶ nginx :8080 ───┼──▶ app2 (172.28.0.12) ─┼──▶ LocalStack DynamoDB (table items)
       round robin       └──▶ app3 (172.28.0.13) ─┘
```

1. **Контейнеризація** (`app/Dockerfile`): той самий `core.py` з ЛР-8 + HTTP-сервер `server.py` (stdlib) і boto3; контекст збірки `labs/`.
2. **3 екземпляри** з `INSTANCE_ID=app-1/2/3`: ідентифікатор у тілі відповіді та заголовку `X-Instance-Id`.
   Сервер однопотоковий, `WORK_MS=20` імітує обробку — один екземпляр має обмежену пропускну здатність, що робить ефект масштабування помітним.
3. **nginx** (`nginx/nginx.conf`): `upstream` з 3 серверами, round robin, пасивна перевірка `max_fails=1 fail_timeout=10s`,
   `proxy_next_upstream error timeout http_502/503/504` + `proxy_next_upstream_tries 3`, `proxy_connect_timeout 500ms`,
   заголовок `X-Upstream`, лог з `upstream_addr`/`upstream_status`. Статичні IP у мережі compose — щоб після рестарту контейнер мав ту саму адресу.
4. **`/health`** у кожному екземплярі (+ `HEALTHCHECK` у Dockerfile, `/nginx-health` у балансувальнику).
5–8. `loadtest.py` (без залежностей) — розподіл за екземплярами, RPS, p50/p95; `experiment.sh` — весь сценарій.

```bash
cd labs/lab09-load-balancing
docker compose up -d --build
./experiment.sh
```

## Висновки

1. **Розподіл** — round robin дає майже рівний розподіл (33/32/35%).
2. **Відмова екземпляра** — nginx виключає сервер після першої невдачі (`max_fails=1`) і повторює запит на іншому
   (`proxy_next_upstream`), тому клієнти майже не бачать помилок. Ціна — затримка першого запиту до «мертвого» сервера
   (`proxy_connect_timeout` 500 мс → p95 зростає до ~560 мс); 2 помилки з 300 — запити, що потрапили у вікно, коли
   обидві спроби завершились таймаутом.
3. **Відновлення** — після `fail_timeout` (10 с) nginx знову пробує app2, і розподіл повертається до ~1/3.
4. **З балансуванням vs без** — пропускна здатність ×3,3 (99 vs 30 RPS), p50 вдвічі менша; один екземпляр —
   єдина точка відмови (100% помилок при зупинці), три за балансувальником — 0%. Без балансування один запит упав по
   таймауту 10 с — переповнилась черга з'єднань однопотокового сервера.
5. Пасивна перевірка nginx open source не має активних health-check-ів; для них — nginx Plus, HAProxy, Traefik
   або (в Kubernetes) readiness-проби + Service, як у ЛР-3.
